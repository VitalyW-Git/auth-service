# 0001. Сначала миграция, потом сущности

- **Статус:** принято
- **Дата:** 2026-10-11

## Контекст

Изначально схема строилась от сущностей: сущность MikroORM → `migration:create` генерирует SQL → применение.
Генератор сравнивает сущности не с базой, а со снимком схемы (`.snapshot-*.json`). Снимок легко расходится с
базой: после удаления сгенерированной миграции без отката снимка новая генерация выдала только правки
комментариев вместо создания таблиц. Кроме того, структуру таблиц хочется видеть и принимать явным SQL
до того, как на ней строится бизнес-логика.

## Решение

Источник истины для схемы — **миграция и применённая по ней база**. Порядок:

1. Проверка на наличие (`.claude/skills/db-table/scripts/check_exists.py`) и согласование проекта схемы.
2. Пустая миграция: `npm run migration:create -- -b -n <Имя>`.
3. В неё пишется явный SQL (`up()` и обратный `down()`), миграция проверяется и при необходимости правится.
4. Применение: `npm run migration:up`.
5. Persistence-сущности пишутся под фактическую схему базы.
6. `npm run migration:check` — сущности совпадают с базой.
7. Затем доменный слой и бизнес-логика.

Снимок схемы отключён: `migrations.snapshot: false` в `src/config/mikro-orm.config.ts`, файл снимка удалён.
Без снимка `migration:create` и `migration:check` сравнивают сущности с живой базой.

## Последствия

- Объекты, которые MikroORM не описывает (exclusion-ограничения, расширения), пишутся в миграции напрямую.
  Если их индекс виден в базе, его нужно объявить в сущности, иначе `migration:check` сочтёт его лишним
  (пример — `appointments_doctor_id_no_overlap`, см. [0008](0008-appointment-time-model.md)).
- PostgreSQL переписывает выражения `check` (`between 1 and 7` → `(weekday >= 1) AND (weekday <= 7)`).
  В `@Check` сущности выражение пишется в нормализованной форме, сверяясь с `pg_get_constraintdef`.
- Генерировать миграции и сверять схему можно только при поднятой базе, в которой применены все миграции.
- Применённую миграцию не редактируют: исправление — новая миграция.

## Отвергнутые варианты

- **Сущности первыми + генератор.** SQL не виден до генерации, снимок расходится с базой.
- **Оставить снимок при порядке «миграция → сущности».** Даже пустая миграция (`-b`) перезаписывает снимок
  текущими сущностями, поэтому снимок всегда отставал бы от базы и генератор выдавал бы повторные `create table`.
