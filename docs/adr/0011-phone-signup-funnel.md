# 0011. Воронка записи по телефону: аккаунт создаётся кодом из SMS

- **Статус:** принято
- **Дата:** 2026-10-12

## Контекст

Пациенты приходят по ссылкам из соцсетей и рекламных предложений, чаще с телефона. Регистрация по email и паролю
перед записью теряет таких пациентов. Мобильный макет «Запись пациента» уже построен как короткая воронка:
услуга → врач и время → имя и телефон → код из SMS → «Вы записаны».

[ADR 0007](0007-patients-per-clinic.md) требовал входа по email и паролю, а вход по телефону откладывал. Онлайн-запись
по-прежнему допустима только с подтверждённым телефоном.

## Решение

- **Два пути к онлайн-записи:**
  - **воронка** — имя и телефон, затем код из SMS. Ввод кода подтверждает телефон, создаёт аккаунт или находит
    существующий, создаёт запись и сессию;
  - **полный вход** — email и пароль или OAuth. Перед первой онлайн-записью пациент подтверждает телефон.
- **Аккаунт без email и пароля.** `users.email` и `users.password` становятся nullable, у OAuth-пользователей
  пароль хранится как `NULL`, а не `''`. Новый способ входа `PHONE` в `users_method_check`.
  - `users_contact_check`: у аккаунта есть email или телефон.
  - `users_phone_method_check`: у аккаунта `PHONE` телефон всегда подтверждён. Сменить номер можно, только
    подтвердив новый.
- **Вход по телефону.** Повторный вход в аккаунт `PHONE` — телефон и код из SMS.
- **SMS-коды хранятся в `tokens`.** `tokens.email` становится nullable, добавлена `tokens.phone`, новый тип
  `PHONE_VERIFICATION`. `tokens_recipient_check`: у кода из SMS есть только телефон, у остальных токенов — только email.
- **Код подтверждает владение номером:**
  - номер уже подтверждён в каком-то аккаунте → это вход в этот аккаунт, запись создаётся на него;
  - номер указан, но не подтверждён в другом аккаунте → номер переходит к тому, кто ввёл код,
    у прежнего аккаунта `phone` очищается;
  - в клинике есть карточка с этим телефоном, заведённая сотрудником → карточке проставляется `user_id`,
    новая не создаётся.

## Последствия

- Миграция `PhoneSignup`: изменения `users` и `tokens`.
- Модуль `auth`: команды отправки и проверки кода из SMS, вход по телефону, провайдер SMS.
- Код, который читает `users.email` и `users.password`, должен учитывать `NULL`. Вход по паролю
  для аккаунта без пароля невозможен. Костыль `''` в `UserRepository.toEntity` убирается.
- `users.is_verified` по-прежнему означает подтверждённый email. У аккаунта `PHONE` он `false`,
  и это не должно блокировать вход по телефону.
- `tokens.token_hash` уникален, а коды из SMS короткие: HMAC одинакового кода у разных номеров совпадёт.
  Поэтому хеш кода из SMS считается от пары «телефон + код». Схема от этого не меняется.
- Публичная отправка SMS требует защиты: лимиты на номер и на IP, reCAPTCHA на отправку кода.
- Время могут занять, пока пациент вводит код. База отклонит вставку
  (`appointments_doctor_id_no_overlap`), и нужен экран «Время уже занято».

## Отвергнутые варианты

- **Только полный вход (ADR 0007).** Лишние шаги для пациента из рекламы и соцсетей. Воронка по телефону — стандарт
  сервисов записи к врачу.
- **Запись гостя без аккаунта.** Пациент не увидит «Мои записи» и не сможет отменить запись сам. Требование
  подтверждённого телефона пришлось бы проверять без аккаунта.
- **Отдельная таблица для кодов из SMS.** Повторяла бы `tokens` (хеш, срок, попытки) ради одной колонки получателя.
- **Технический email вида `+7916…@phone.local`.** Скрывает в данных отсутствие email и ломает уникальность,
  если пациент потом добавит настоящий.
